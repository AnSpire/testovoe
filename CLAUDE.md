# Контекст проекта для агента

Это тестовое задание (см. формулировку ниже), выполняется поэтапно. Этот файл —
чтобы другой агент/сессия мог продолжить без повторного объяснения со стороны
пользователя. **Пользователь не работал с Vagrant/Ansible до этого проекта** —
объяснения в диалоге должны оставаться на уровне новичка, команды — копипастные.

## Формулировка задания (пункты a–h)

- **a** — Python-веб-приложение (`main.py`, FastAPI), два эндпоинта:
  `POST /` → `Hello, World!` если заголовок `Test: Hello`, иначе `403`;
  `GET /health` → пингует `77.88.8.8`, `200/"OK"` при успехе.
- **b** — Ubuntu 22.04 VM, деплой приложения через systemd от имени отдельного
  системного пользователя.
- **c** — Dockerfile для приложения, собрать образ.
- **d** — docker-compose (app + prometheus + alertmanager) **+** отдельная Ubuntu
  22.04 VM с двумя сетевыми интерфейсами (внешний+внутренний) и NAT-роутингом
  из внутренней сети во внешнюю.
- **e** — перенести VM из пункта b в внутреннюю сеть, настроить выход во внешний
  мир через NAT на VM из пункта d.
- **f** — 3 VM Ubuntu 22.04, развернуть 3-узловой Kubernetes-кластер.
- **g** — задеплоить приложение в кластер.
- **h** — Ingress для внешнего доступа — **явно без `kubectl port-forward`**.

## Согласованная группировка на три независимые лабы

1. **Lab 1 (NAT)** — `infra/nat-lab/`: a → b → d2 (NAT-часть) → e.
   Vagrant+libvirt, две VM: `app` (систему, пользователь, systemd) и `gateway`
   (2 NIC, NAT/MASQUERADE), затем `app` переносится во внутреннюю сеть.
2. **Lab 2 (Docker)** — готова: c → d1 (Dockerfile + docker-compose с
   prometheus/alertmanager). Живёт **в корне репозитория** (не в `infra/` —
   это не VM-лаба), рядом с `main.py`. Без VM, прямо на хосте.
3. **Lab 3 (Kubernetes)** — готова: f → g → h. `infra/k8s-lab/`, 3 VM через
   Vagrant+libvirt (одна сетевая карта у каждой — дефолтная NAT-сеть
   vagrant-libvirt), kubeadm-кластер (1 control-plane + 2 worker, Calico в
   VXLAN-режиме, не BGP — см. грабли), деплой `anspire/testovoe-app:latest`
   из Docker Hub, MetalLB (L2) + ingress-nginx для внешнего доступа без
   `kubectl port-forward`.

## Ключевые решения (уже согласованы с пользователем, не пересматривать без причины)

- Провайдер Vagrant: **libvirt/KVM** (не VirtualBox) — хост Arch Linux.
- Kubernetes: **kubeadm** (не k3s), 1 control-plane + 2 worker.
- Внешний доступ к Ingress (пункт h): **MetalLB (LoadBalancer) + ingress-nginx**,
  не NodePort.
- Vagrant box: **generic/ubuntu2204**.
- Приложение на VM запускается через **uv** (не pip/venv) — `uv sync --frozen` +
  `uv run uvicorn`. Так удобнее: `uv` сам тянет Python 3.13 (т.к. `pyproject.toml`
  требует `>=3.13`, а Ubuntu 22.04 несёт только 3.10), не трогая системный Python.
- Стиль работы с пользователем: **спрашивать перед ключевыми архитектурными
  решениями** (через AskUserQuestion), не решать единолично. Мелкие детали
  реализации — можно сразу делать.
- Lab 2 (Docker, c+d1) — Dockerfile/docker-compose.yml/`monitoring/` лежат в
  **корне репозитория**, не в `infra/` (это не VM-лаба).
- В `main.py` добавлен `GET /metrics` через `prometheus-fastapi-instrumentator`
  (две строчки, не трогает требуемое поведение `POST /` / `GET /health`) —
  чтобы Prometheus реально скрейпил приложение, а не просто проверял, что
  порт открыт.
- Образ приложения пушится в **Docker Hub** под `anspire/testovoe-app` (не
  свой self-hosted registry) — `docker login` сделан пользователем заранее.
  Lab 3 (Kubernetes) тянет оттуда же этот образ, не пересобирает заново.
- Lab 3: у всех 3 VM **одна** сетевая карта (дефолтная NAT-сеть
  vagrant-libvirt), не две, как в Lab 1. Отдельная внутренняя сеть под
  кластер не нужна и не помогает — причина сетевых обрывов была не в
  количестве интерфейсов, а в BGP-режиме Calico (см. грабли ниже).
- Lab 3: CNI — **Calico в VXLAN-режиме** (`calico-vxlan.yaml`), не
  стандартный BGP-манифест (`calico.yaml`) — на флэт-сети, где все ноды
  делят одну подсеть, BGP-режим ломает внешнюю сеть нод (грабля №7 ниже).

## Грабли, на которые наступали (чтобы не наступать повторно)

Среда: хост — Arch Linux, libvirt/KVM, одновременно установлен Docker. Все
проблемы ниже всплыли при первом `vagrant up`/`vagrant provision` для VM `app`
и были замаскированы друг другом — решались по очереди, каждая следующая
проявлялась только после фикса предыдущей.

1. **Docker ломает NAT других libvirt-сетей.** Docker ставит глобальную политику
   `FORWARD DROP` в iptables/nftables и пропускает только свой трафик — через
   отдельную таблицу `ip filter`, которая выполняется на том же netfilter-хуке,
   что и правила libvirt, и перекрывает их `ACCEPT`. Симптом: `vagrant ssh` работает
   (SSH — локальный трафик до хоста), но у VM нет доступа в интернет, пинги/apt
   зависают намертво без ответа. Диагностика: `sudo nft list table ip filter` →
   смотреть `chain FORWARD { policy drop; jump DOCKER-USER; jump DOCKER-FORWARD; }`.
   **Фикс (на хосте, не в Ansible, разовый):**
   ```bash
   sudo iptables -I DOCKER-USER -i virbr1 -j ACCEPT
   sudo iptables -I DOCKER-USER -o virbr1 -j ACCEPT
   ```
   (не персистентно между перезагрузками хоста — если после ребута снова не
   будет интернета у VM, это первое, что проверять).

2. **`vagrant-libvirt` сеть может "зависнуть" с нерабочим NAT без явных ошибок.**
   `sudo virsh net-destroy`/`net-start` одной сети иногда не переподключает
   нормально bridge к уже существующему VM (bridge может остаться `DOWN`,
   `vnet*` не в мосту). Если простой restart сети не помогает — надёжнее
   полностью снести определение сети и дать `vagrant up` пересоздать её:
   ```bash
   vagrant halt app
   sudo virsh net-destroy vagrant-libvirt
   sudo virsh net-undefine vagrant-libvirt
   vagrant up app
   ```

3. **Бокс `generic/ubuntu2204` несёт мёртвые DNS-сервера, зашитые статически.**
   `4.2.2.1`, `4.2.2.2`, `208.67.220.220` — старые публичные резолверы, прописаны
   сразу в двух независимых местах: `/etc/netplan/01-netcfg.yaml` (nameservers) и
   `/etc/systemd/resolved.conf` (`DNS=`). ICMP/TCP к этим адресам отвечает (хосты
   живы), но DNS-сервис на них не отвечает — отсюда ложное ощущение "сеть
   работает, а DNS не работает необъяснимо". Пофикшено в Ansible-роли
   `app_deploy` (задачи "Fix stale DNS..." в `tasks/main.yml`) — патчит оба файла
   на `8.8.8.8`/`1.1.1.1`.

4. **Тот же бокс несёт `DNSSEC=yes` в resolved.conf, что рвёт резолвинг через
   этот NAT.** `resolvectl query` показывал `DNSSEC validation failed:
   missing-key`. Для лабораторного стенда DNSSEC не нужен — отключили
   (`DNSSEC=no`) той же ролью.

5. **Ansible `become_user` на пользователя без шелла (`/usr/sbin/nologin`) падает
   с ошибкой BSD-ACL.** При установке `uv` от имени `appuser` Ansible пытается
   выставить права на temp-файлы через `chmod +a` (это macOS/BSD NFSv4 ACL
   синтаксис), которого нет в Linux → `chmod: invalid mode:
   'A+user:appuser:rx:allow'`. Фикс — `infra/nat-lab/ansible.cfg`:
   ```ini
   [defaults]
   allow_world_readable_tmpfiles = True
   ```

6. **`vagrant-libvirt` `private_network` по умолчанию создаёт свою NAT-сеть с
   собственным IP/DHCP на мосту хоста — и это может совпасть с адресом,
   который вы вручную дали VM.** При добавлении внутренней сети для
   `gateway`/`app` (`192.168.56.0/24`) оказалось, что сама libvirt-сеть
   (`forward mode='nat'`) заняла `192.168.56.1` на мосту хоста — тот же
   адрес, что получил интерфейс `gateway`. Симптом: прямой пинг на `.1`
   работал (отвечал либо хост, либо VM), но транзитный трафик (`ping
   1.1.1.1` с `app`) пропадал без следа — пакет виден в `tcpdump` на
   исходящем интерфейсе `app`, но не доходит до `gateway` вовсе, при
   абсолютно верных `FORWARD`/`ip_forward` правилах на `gateway`. Диагностика:
   `sudo virsh net-dumpxml <network-name>` → смотреть `forward mode` и
   `<ip>`/`<dhcp>`. **Фикс** — явно отключить автоматику у `private_network`
   в Vagrantfile:
   ```ruby
   libvirt__forward_mode: "none",
   libvirt__dhcp_enabled: false,
   libvirt__host_ip: "<свободный адрес, не совпадающий с VM>"
   ```
   Если сеть уже была создана с неправильными параметрами — Vagrant её не
   переконфигурирует сам, нужно пересоздать (как в пункте 2 выше):
   ```bash
   vagrant halt <машины>
   sudo virsh net-destroy <network-name>
   sudo virsh net-undefine <network-name>
   vagrant up <машины>
   ```
   Подробности и полный разбор — `infra/nat-lab/reports/d2-e-nat-gateway.md`.

Все фиксы 3–6 уже в репозитории и применяются автоматически (для фикса 6 —
нужное состояние уже заложено в текущем Vagrantfile, пересоздавать сеть нужно
только если кто-то создал её руками/по старой версии файла). Фикс 1 (и иногда
2) нужно проверять/повторять руками на хосте, если это новая машина или после
перезагрузки — Ansible их не делает, это настройка хоста, а не VM.

7. **(Lab 3) Calico в BGP-режиме на флэт-сети ломает внешнюю сеть нод.**
   Самая серьёзная находка в этом проекте. Когда несколько нод Kubernetes
   делят одну L2-подсеть (а они её всегда делят — это их единственный
   способ общаться), демон BIRD (BGP-протокол Calico) по умолчанию
   анонсирует соседям **все** свои "прямые" маршруты, включая маршрут до
   собственной внешней/NAT-подсети — не только pod-сети. Каждая нода
   анонсирует одну и ту же подсеть как "свою", соседи ставят к ней
   /32-маршрут через оверлей — и получается более специфичный (и
   неправильный) путь к адресу, который на самом деле напрямую доступен.
   Симптом: SSH/интернет на ноде периодически полностью пропадает без
   видимых причин (`ip route` показывает дублирующийся маршрут,
   `proto bird`, к адресу шлюза). **НЕ лечится** добавлением второй
   (внутренней) сетевой карты или настройкой `IP_AUTODETECTION_METHOD` —
   это влияет только на то, какой адрес Calico считает "своим", а не на
   то, что BIRD анонсирует наружу. **Фикс** — использовать VXLAN-режим
   Calico вместо BGP: манифест `calico-vxlan.yaml` вместо `calico.yaml`
   (ставит `calico_backend: "vxlan"` — BIRD в этом режиме не запускается
   вообще, маршруты программируются статически через датастор). Подробный
   разбор — `infra/k8s-lab/reports/f-k8s-cluster.md`.

8. **IPv6 happy-eyeballs ловит таймаут при пулле образов с Docker Hub.**
   Бокс имеет включённый, но нерабочий IPv6. `docker.io` отдаёт AAAA-запись,
   containerd иногда сначала пробует IPv6, получает `cannot assign
   requested address`, откатывается на IPv4 — внешне выглядит как
   случайный `ImagePullBackOff`/`CrashLoopBackOff`, который сам
   самовосстанавливается через backoff. Фикс — отключить IPv6 на нодах
   целиком через sysctl (`net.ipv6.conf.all.disable_ipv6 = 1` и `default`).

9. **MetalLB `IPAddressPool.spec.addresses` не принимает одиночный IP без
   маски/диапазона.** Нужно `x.x.x.x/32`, а не голый `x.x.x.x` — иначе
   admission webhook отклоняет ресурс с ошибкой "invalid CIDR".

10. **На DHCP-сети vagrant-libvirt адреса не раздаются по порядку с начала
    диапазона** — предположение "последние адреса подсети свободны" не
    гарантировано и реально ловило коллизию (одна из нод получила именно
    тот IP, что был отведён под MetalLB). Если нужен гарантированно
    свободный диапазон на такой сети — проверять через ping каждый кандидат
    и исключать IP уже существующих машин, а не просто брать фиксированный
    хвост диапазона.

## Практические заметки

- `sudo` в этом окружении агент **не может выполнить сам** (нет интерактивного
  TTY для пароля) — любую команду с `sudo` на **хосте** просит выполнить
  пользователь вручную (через `!команда` в Claude Code) и прислать вывод. Внутри
  VM это не проблема — Ansible `become: true` работает (passwordless sudo для
  `vagrant`-пользователя на госте).
- Долгие команды (`vagrant up`, `vagrant provision`) занимают от пары минут до
  10+ — запускать их в фоне (`run_in_background: true`), **не оборачивать в
  `timeout`** (иначе процесс просто убьётся раньше, что уже случилось один раз
  и выглядело как "зависание", а было самоубийством по таймауту обёртки).
  Прогресс отслеживать через `ps aux | grep ansible-playbook` / `vagrant ssh`,
  не через попытки читать файл вывода фоновой задачи вручную.
- IP VM `app` при текущей конфигурации: `192.168.121.242` (DHCP, но стабильный
  для данной сети) — лучше перепроверять через `vagrant ssh app -c "hostname -I"`,
  а не считать захардкоженным навечно.
