# Пункт f — 3-узловой кластер Kubernetes (kubeadm)

## Задача

3 VM Ubuntu 22.04, развернуть на них 3-узловой кластер Kubernetes.

## Расположение

```
infra/k8s-lab/
  Vagrantfile              # 3 VM: k8s-master, k8s-worker1, k8s-worker2
  ansible.cfg
  ansible/
    group_vars/all.yml
    site.yml
    roles/
      box_dns_fix/   # та же роль, что в Lab 1 (дохлые DNS/DNSSEC в боксе)
      common/        # swap off, containerd, sysctl, модули ядра
      kubeadm_pkgs/  # kubelet/kubeadm/kubectl из pkgs.k8s.io
      k8s_master/    # kubeadm init + Calico + join-команда
      k8s_worker/    # kubeadm join
      k8s_apps/      # MetalLB + ingress-nginx + деплой приложения (g, h)
  manifests/          # Deployment/Service/Ingress приложения
  reports/
```

## Топология сети

У каждой из 3 VM **одна** сетевая карта — дефолтная NAT-сеть vagrant-libvirt
(она же даёт интернет для apt/containerd). Изначально у каждой ноды было
по два интерфейса (внешний + отдельная приватная сеть под кластер, по
аналогии с Lab 1), но от этого отказались — подробности в разделе
"Грабли" ниже, это была не мелочь, а основная причина, по которой кластер
изначально не вставал.

## kubeadm

- Версия Kubernetes: 1.30, пакеты из `pkgs.k8s.io` (новый официальный репозиторий,
  `apt.kubernetes.io` устарел), `apt-mark hold` после установки.
- `containerd` как CRI, `SystemdCgroup = true` в `/etc/containerd/config.toml`
  (обязательно для кублета, иначе конфликт cgroup-драйверов).
- `kubeadm init --apiserver-advertise-address=<IP ноды> --pod-network-cidr=192.168.0.0/16`
  на `k8s-master`, затем `kubeadm token create --print-join-command`,
  результат передаётся воркерам через Ansible `set_fact`/`hostvars` в рамках
  одного прогона playbook (мастер и воркеры — разные play в одном
  `site.yml`, факты между play в одном прогоне доступны всем хостам).
- CNI — **Calico**, но не стандартный BGP-манифест, а VXLAN-вариант
  (`calico-vxlan.yaml`) — почему, см. ниже.

## Multi-machine Ansible с одной машины

Vagrant поднимает все 3 VM, но Ansible-провижининг навешен только на
**последнюю** (`k8s-worker2`, `ansible.limit = "all"`) — стандартный
Vagrant-паттерн для multi-machine Ansible: к моменту провижининга все 3 VM
уже существуют, inventory видит их все сразу, один прогон `ansible-playbook`
конфигурирует весь кластер.

## Грабли, на которые наступили (самое важное в этой лабе)

### 1. Calico в BGP-режиме на флэт-сети ломает внешнюю сеть нод

**Симптом:** периодически (через минуту-две после `kubeadm join` или после
установки MetalLB) внешняя сеть ноды (та самая, через которую к ней ходит
Vagrant/SSH и интернет) полностью пропадала — ICMP/SSH с хоста перестают
доходить, хотя сама VM жива и работает.

**Диагностика:** `ip route` на зависшей ноде показывал ДВА маршрута к
одному и тому же адресу (адресу шлюза внешней сети):
```
192.168.121.1 proto bird
	nexthop via 10.10.10.11 dev eth1 weight 1
	nexthop via 10.10.10.12 dev eth1 weight 1
192.168.121.1 dev eth0 proto dhcp scope link src 192.168.121.47
```
Первый (`proto bird`, /32, через соседние ноды) **более специфичен**, чем
второй (`/24`, напрямую), и Linux всегда выбирает более специфичный
маршрут — то есть пакеты к шлюзу уходили не напрямую через свой `eth0`, а
"в гости" к соседней ноде через Calico-оверлей, где терялись.

**Корень проблемы:** Calico (BIRD, демон BGP-протокола) по умолчанию
анонсирует соседним нодам **все** маршруты от "прямого" протокола
(`protocol direct { interface -"cali*", -"kube-ipvs*", "*"; }` в
confd-шаблоне bird.cfg) — то есть не только pod-сети, а вообще все
локально подключённые сети ноды, включая её собственную внешнюю/NAT-сеть.
Поскольку **все три ноды сидят на одной и той же подсети** (что
естественно — это их общая "материнская" сеть), каждая нода анонсирует её
как "свою", соседи ставят к ней маршрут через BGP-мешап — и получается
циклический/некорректный путь к адресу, который на самом деле напрямую
доступен без всякой маршрутизации.

Первая попытка исправить (`IP_AUTODETECTION_METHOD=interface=eth1`, отдельная
внутренняя сеть под кластер) не помогла — эта настройка влияет только на то,
какой адрес Calico считает "своим", а не на то, что BIRD анонсирует наружу.
Переход на единственную сетевую карту тоже не избавил от бага — пока BGP
включён, проблема воспроизводится при ЛЮБОЙ топологии, где ноды делят общую
L2-сеть (а они её всегда делят — это их единственный способ общаться).

**Настоящий фикс:** использовать VXLAN-режим Calico вместо BGP —
`calico-vxlan.yaml` вместо `calico.yaml` (`calico_backend: "vxlan"` в
ConfigMap). В VXLAN-режиме BIRD не запускается вообще — маршруты до
pod-подсетей других нод Calico программирует статически через собственный
датастор (etcd/Kubernetes API), без какого-либо протокола динамической
маршрутизации, поэтому паразитных BGP-анонсов просто не бывает.

### 2. Docker блокирует NAT свежей libvirt-сети (та же грабля №1, что в Lab 1)

Каждый раз после перезагрузки хоста Docker заново ставит `FORWARD DROP` и
перехватывает трафик новой libvirt-сети раньше правил `vagrant-libvirt`.
Фикс (разовый, на хосте, не персистентный между перезагрузками):
```bash
sudo iptables -I DOCKER-USER -i virbr1 -j ACCEPT
sudo iptables -I DOCKER-USER -o virbr1 -j ACCEPT
```
(`virbr1` — реальное имя моста дефолтной сети `vagrant-libvirt` в этой
сессии; уточнять через `sudo virsh net-dumpxml vagrant-libvirt`).

### 3. IPv6 happy-eyeballs ловит таймаут при пулле образов с Docker Hub

Бокс имеет включённый (хотя нерабочий) IPv6. `docker.io` отдаёт DNS-ответ
с AAAA-записью, и containerd иногда сначала пробует IPv6 (RFC 6724 "happy
eyeballs"), ловит `connect: cannot assign requested address` (нет реального
IPv6-маршрута) и только потом откатывается на IPv4 — что проявляется как
кратковременный `ImagePullBackOff`/`CrashLoopBackOff` у подов, тянущих
образы с Docker Hub (включая `calico/node` и наш собственный
`anspire/testovoe-app`). Само по себе не фатально (kubelet делает backoff
retry и в итоге пуллит через IPv4), но добавляет случайную задержку.
**Фикс** — в роли `common` отключили IPv6 на нодах целиком:
```
net.ipv6.conf.all.disable_ipv6  = 1
net.ipv6.conf.default.disable_ipv6 = 1
```

### 4. MetalLB `IPAddressPool.spec.addresses` не принимает одиночный IP без маски

`kubectl apply` падал с `admission webhook ... denied the request: invalid
CIDR "192.168.121.241"` — MetalLB ожидает либо CIDR (`x.x.x.x/32`), либо
диапазон (`a-b`), но не голый IP. Фикс — дописывать `/32` к каждому адресу
в шаблоне `metallb-pool.yaml.j2`.

### 5. Выбор свободных IP для пула MetalLB — не гарантированно свободен и не идемпотентен

Единственная сеть нод — DHCP-сеть vagrant-libvirt, адреса раздаются не по
порядку (не "с начала диапазона", как изначально предполагалось) — ловили
реальную коллизию, когда один из узлов DHCP-получил именно тот адрес, что
был отведён под MetalLB. Решение — Ansible на лету (в роли `k8s_apps`)
строит список кандидатов (адреса `.240`–`.249` той же подсети), выкидывает
из него IP самих 3 нод и всё, что отвечает на `ping`, и берёт первые 3
оставшихся. Дополнительно: это делается **только один раз** (проверка
`kubectl get ipaddresspool` перед пересчётом) — иначе каждый повторный
`vagrant provision` пересчитывает новый набор адресов (старые уже "заняты"
самим MetalLB и не проходят ping-проверку), из-за чего внешний IP
приложения менялся бы при каждом re-provision без необходимости.

### 6. Случайные одноразовые сетевые таймауты с внешними хостами

Несколько раз по ходу работы ловили единичные `Connection failure: read
operation timed out` / `SSL handshake timed out` при скачивании apt-ключа с
`pkgs.k8s.io` конкретно с одной из VM — непостоянно, при повторе сразу
проходило. Похоже на обычную сетевуюflakiness NAT-соединения, не
специфично для этого проекта. Поскольку повторный прогон каждый раз заново
дёргал сеть за этим ключом, добавили проверку (`stat` на итоговый
keyring-файл) — если ключ уже был успешно скачан и обработан в прошлый
прогон, повторно его не трогаем.

## Проверка результата

```
$ kubectl get nodes
NAME          STATUS   ROLES           VERSION
k8s-master    Ready    control-plane   v1.30.14
k8s-worker1   Ready    <none>          v1.30.14
k8s-worker2   Ready    <none>          v1.30.14
```

Повторный `vagrant provision` (полный повторный прогон всего `site.yml` на
уже работающем кластере) проходит **полностью идемпотентно**: `failed=0`
на всех трёх нодах, пул MetalLB и внешний IP приложения не меняются.
